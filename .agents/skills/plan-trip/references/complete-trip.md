# 完整差旅的交付契约

适用：安排企业出差、提交完整行程、在行程卡修改会场。仅查车票、单独问标准或查询记忆时不加载本流程。

## 主 Agent 与运行时

1. 保存并验证当前行程；缺基本字段或目的地内的已验证会场时使用行程确认卡。禁止把自由文本或其他城市 POI 当成已确认会场。
2. `prepare_trip_options` 是完整交付入口。它读取本人已保存偏好、查询 12306 和高德附近酒店，并按明确排除项决定天气及到站通勤查询。资料不可用要保留其他结果。
3. policy_rag 核实城市等级、住宿档位、餐补、铁路/航空席别及例外条件、市内交通、住宿核算和必要报销凭证。不用其他城市推断，不默认职级。每项事实保留直接来源。已有本轮有效制度可复用，不为追求齐全无限重试。
4. 传递当前版本的制度和真实选项给 trip_planner。不要只传“已查到”的摘要。规划后合并所有相关分区、来源和待确认项，同步纯文本与卡片数据。
5. 用户明确要求合规检查时，再将方案及制度交给 compliance。没有职级、选定席别或实际房价时只能说明未知，不能声称通过合规。

## trip_planner 的输出

你是规划角色时只读取明确传入的 trip、dependencies 和其中的 data.choices，不调度其他角色、不调用主 Agent 工具。

- `data.itinerary.days` 使用真实日期及 `activities` 文本数组，覆盖本次各日。写明去程候选、工作地点、附近住宿和返程需确认的安排。
- 每日活动围绕工作安排简洁表达；车次表已经展示全部余票，不在日程重复四趟车的全部席别库存。交通只提与该日安排有关的候选及约束。
- 车次、日期、到达站、酒店必须来自当前选项；未被用户选择的车次和酒店始终称候选。没有返程查询结果时不得捏造返程班次。
- 缺会议开始/结束时间时，列出 `missing_info`，不安排虚构会议、不承诺准时抵达。出现明确时间冲突时解释冲突，不静默安排迟到。
- 制度规则保留职级、城市、时长和例外条件。偏好不是资格；酒店 POI 的参考消费不是入住日房价，也不能据此判定合规。
- `data.decision_basis` 解释选择依据；重要未知项进入 `missing_info`。缺少规划所需条件时状态用 partial，仍交付有依据的安排。

## 展示与完成条件

卡片按行程概览、会场与酒店地图、车次、每日安排、关键差标、待确认项组织。金额与单位醒目，适用条件紧随；详细条款和可读来源按需展开。不要显示内部来源编号或各 Agent 的工作汇报，不重复堆叠同一摘要。

完整行程必须实际执行制度查询与日程规划，或者复用同版本有效结果。只有车次/酒店成功不等于整轮 completed；缺资料标 partial 并说明缺项。修改会场需重新查附近酒店并规划，旧卡保留旧地点对应结果，不能把旧酒店挪到新会场。
