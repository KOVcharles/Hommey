# 出差入口、上下文和制度交付回归修复

## 从实际执行记录确认的问题

用户反馈的重庆请求 `54c4ed22-236d-4043-a1ea-1fe1f194f8d8`：主 Agent 已正确委派制度角色，
失败发生在制度子 Agent。四轮内进行了五次检索，每次工具消息约 1.1–1.2 万字符，
另有多次来源回读。运行器把整段消息再次 JSON 序列化后与 80,000 字符比较，超过便失败。
因此这个错误不是用户问题过大，也不能据此归因于主 Agent 加载了全部历史。

“chuchai”请求：主 Agent 连续尝试不存在的 Skill 名称，子 Agent 也猜测 Skill 名称。
整轮共 12 次模型调用。read_skill 的 schema 原先只暴露任意字符串，没有可选名称。
最后 finish 没有选择行程结果；原表单生成条件还要求非空行程，所以空行程退化为文字问题。

实际模型验证又发现：缩短检索输出后，仍可能重复委派，耗时 134.746 秒；子任务 summary
只说“已查到”，具体数据没有进入展示层。这证明只提高上下文上限、缩短文本或修改提示词均不足以解决体验问题。

## 实现边界

- 明确且无附加任务的“出差 / chuchai / 我要出差”等入口，直接根据当前会话状态生成现有交互表单，零模型调用。
  不填默认日期，不写虚构行程，不吞掉制度、天气、取消、历史等混合请求；有附件时保留完整 agent 路径。
- Skill 名称由工具 schema 枚举给出，子角色只能看到本角色名称。业务方法不清楚时才加载 Skill。
- 明确、单一的“去某城市出差，查询差旅标准”直接进入一个制度子任务，复用同一取消、检查点、来源和渲染链路。
  不额外调用主模型规划和重新委派；复杂或混合表达仍由主 Agent 处理。
- RAG/记忆检索返回 450 字符以内的发现索引，同一来源去重；完整原始资料仍在当前任务的私有来源仓库中。
  制度检索可附带短来源的完整 evidence（单条不超过 2,500 字符，每次检索合计不超过 7,000 字符），
  明确标为已回读，避免用一个模型回合重复请求同一段短资料。长来源继续分页。
- 回读默认 4,000 字符、最多 6,000 字符。长记录返回明确的片段范围和 next_offset，不能默认为已读完整条款。
  RAG 回读移除重复文本和检索诊断，保留内容与制度元数据；不删除未知名称的适用条件字段。
- 每轮调用前，超过 32,000 字符时清理较早的大型工具观察内容，保留工具调用/结果配对和可回读的来源 ID。
  最新工具批次必须先给模型看过一次，因此 32,000 是压缩目标而非截断阈值。
  原请求、原始来源、已验证结果和写入回执不随清理删除。80,000 字符只作为最后保护，计算包含工具 schema。
- 子 Agent 完成语义提取，主 Agent 获得摘要、结构化关键事实和引用。制度/记忆 data 上限为 4,000 字符。
- 制度报告必须给出 findings：具体结论（金额含单位）、适用条件、逐项 evidence_refs。
  报告和单项引用都经过校验，partial 也不能引用未回读资料。前端直接渲染 findings，避免“已查到但没展示”。
- 制度子任务最多四轮：首轮只开放检索，随后只开放回读/报告，末轮只允许报告；
  第五轮仅用于修正报告格式，不可继续检索。工具执行端也拒绝越阶段调用。独立只读查询可以并发。子任务自身轮数/上下文预算耗尽时，
  返回不可用结果供主任务交付其他部分；全局调用预算与取消仍然向上传播。
- 日志记录每轮角色、消息字符数、工具 schema 字符数和压缩量，不记录资料正文或凭据。
- 模型适配层使用完整原生工具响应，保留未经 JSON repair 改写的原始参数；未完成的 JSON 不可授权写入。
  工具 wire schema 展开嵌套引用，长度约束由后端 Pydantic 执行，关键报告字段明确 required。
  最后一轮指定 report 工具，取消 SDK 的隐式重试；Web 仍实时发送任务进度。

## 设计依据

[Anthropic：Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)
建议从足够简单的方案开始，明确区分可预测流程和需要模型自主判断的任务。这里将明确表单入口
交给确定性代码，复杂差旅请求仍交给主 Agent。

[Anthropic：Effective Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
讨论按需读取、工具结果清理和独立子任务上下文。这里区分两种不同操作：
子 Agent 负责语义总结；运行器负责索引、分页、去重和清理，不能把文本截断冒充有语义的压缩。

## 验证与限制

回归测试覆盖零模型表单、Web 持久化和流式 DTO、重复检索、长记忆分页、私有来源、引用校验、
上下文清理后的工具配对、六角色协作、取消、幂等和模型断连恢复。

真实模型/知识库验收由 `tests/test_supervisor_live.py` 提供，显式设置
`HOMMEY_RUN_LIVE_AGENT_TESTS=1` 后执行；使用隔离测试状态，不修改用户对话和行程。

最终实际重庆请求：35.156 秒，1 个子任务，4 次 LLM 调用和 4 次 RAG 查询，
最大输入（含工具 schema）39,160 字符。成功交付城市分类、住宿、餐补、飞机、高铁和市内交通标准及来源，
没有再次叠加职级上浮。针对当前运行器的 101 项回归测试通过，真实模型报告格式测试通过。
验收还检查重庆二类城市的实际分类、结果项展示、证据和调用数；城市不明时不得拿其他城市举例代替答案。

字符预算不是精确 token 预算；不能从单次实际模型验收推导 p95 延迟或生产 SLA。
外部模型/知识库超时、复杂多意图的端到端正确率、并发负载和数据库容量仍需独立验收。
