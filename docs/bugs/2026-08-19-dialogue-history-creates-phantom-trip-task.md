# 第一部分：Bug 描述

本部分只描述已经发生的现象、已核实的执行链路和根因，不代表修复已经完成。

## 1.1 用户现象

用户先输入“安排一下去广州”，系统返回“我还不太确定这是否与公司差旅有关，
请补充出差目的地、日期……”。随后输入“广州出差计划”，页面却只显示
“广州差旅信息 / 已整理好行程安排”的空行程卡。重复输入后现象继续出现。

## 1.2 已核实的实际链路

1. `安排一下去广州` 没有命中当前快速路由，被 IntentionAgent 判为 `unclear`；
   非 Skill 分支只返回澄清文案，不会创建 workflow run。
2. 第二轮虽然 `FastIntentRouter.route("广州出差计划")` 可以确定识别为
   `itinerary_planning`，但快速路由在存在历史消息时被关闭，消息重新进入 LLM。
3. IntentionAgent Prompt 允许仅凭“对话历史中系统正在收集出差信息”输出
   `event_collection`。上一轮的普通澄清文案因此被误当成真实的 `WAITING_USER` 状态。
4. 独立 `event_collection` 被授权执行；它没有完整行程规划目标，也没有独立暂停契约，
   最终由 Composer 生成空的“行程安排”卡片。

## 1.3 根因

- 同一事实存在两个互相冲突的来源：持久化工作流状态和自然语言聊天历史。
- `event_collection` 同时承担内部能力与用户可识别意图，导致 LLM 可以绕过状态机，
  凭历史文案自行创建“补充信息”任务。
- 明确的当前轮规划请求没有优先于历史上下文；快速路由对有历史会话一律禁用，边界过宽。
- `安排一下去广州` 这种“安排 + 去 + 目的地”的自然表达未被规则识别为规划请求。

## 1.4 任务状态边界

当前问题的关键不是“怎样从聊天内容猜测任务是否结束”，而是系统不应从聊天内容猜测。
任务状态只能来自持久化 orchestration state：

| Run 状态 | 是否属于当前任务 | 处理方式 |
| --- | --- | --- |
| `WAITING_USER` | 是 | 还必须存在对应的 `WAITING_USER` goal 和 wait 记录，才能接收字段补充 |
| `ACTIVE` | 是 | 仅代表当前请求正在执行；旧请求残留的 `ACTIVE` 先按现有恢复机制转为可恢复状态 |
| `INTERRUPTING` / `INTERRUPTED` | 可恢复 | 只有明确继续、修改原目标或与原目标一致时才恢复 |
| `COMPLETED` / `FAILED` / `ABANDONED` / `EXPIRED` | 否 | 新消息按新任务处理 |

`active_trip` 只保存已确认的行程事实，不代表存在未完成任务；助手历史文案只用于理解指代，
不能创建、恢复或结束 workflow。

保持现有 IntentionAgent、TurnResolver、状态机、任务 DAG 和 Composer 主结构，只收紧边界，
不重写意图系统：

```text
状态机决定是否存在旧任务
IntentionAgent 识别新的用户目标
event_collection 只收集行程字段
Composer 只接收可交付的业务结果
```

## 2.9 最终验收要求

- `安排一下去广州` 进入 `itinerary_planning`，缺少字段时显示行程补充卡。
- `广州出差计划` 无论前一轮是否出现普通澄清文案，都不得识别为独立
  `event_collection`。
- 只有存在真实 `WAITING_USER` run 时，离散字段才恢复原目标；终态 run 不再影响新请求。
- 任意 `planning_ready=false` 结果都不能进入最终 Answer Composer 或显示“已整理好行程”。
- 现有车票、天气、政策、偏好和多意图工作流行为不发生回归。
