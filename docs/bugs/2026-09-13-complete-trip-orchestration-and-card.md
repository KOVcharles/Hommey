## 用户现象与复现证据

同一会话中，用户提交北京至南昌两天会议行程并选择西湖区会堂，只收到车次酒店；另问“南昌的差旅标准是什么”后，标准卡出现密集双列粗体、重复摘要和内部来源 ID。

只读核对 `supervisor_runs` 的 checkpoint、工具调用及最终 answer_document：

| 北京时间 | 请求 ID | 实际执行 | 最终卡片 |
| --- | --- | --- | --- |
| 2026-09-13 14:20:46 | `839231d6-4ba2-4b66-94d5-da63079f24d5` | main_round=0，无 policy_rag / trip_planner，0.70 秒完成 | 12 个车次、4 家酒店，只有出行选择分区 |
| 2026-09-13 14:21:12 | `b7bb3b85-1f4d-4d01-9167-b4d266a043e2` | 主 Agent delegate → finish；RAG 4 次搜索、6 次回读 | 六项制度结论全部进入卡片 |

因此不能将两次问题混同：完整行程漏调用；单独制度问答没有在结果传递中漏掉这六项。

## 缺陷清单与根因

### BUG-2026-09-13-01：完整行程仅查询车次酒店即完成

- 严重性：高；状态：当前分支已修复。
- 根因：`engine.prepare_options` 从表单快捷路径或主 Agent 工具调用进入后直接返回 `options_output`，完成状态只看车次/酒店。
- 修复：保留受控入口，补齐 policy_rag → trip_planner。明确向规划角色传入有版本和来源的实际候选、制度与偏好。默认尝试天气和到站通勤，保留用户排除项。明确要求合规时补 compliance。
- Skill：更新 `.agents/skills/plan-trip/SKILL.md`，新增按需加载的 `references/complete-trip.md`；完整分支记录技能读取并向规划角色加载参考正文。
- 完成条件：必需结果缺失、失败或有待确认条件时为 partial/degraded，不能仅凭候选查询成功返回 completed。

### BUG-2026-09-13-02：替换回答时仅保留 policy，纯文本未同步

- 严重性：高；状态：当前分支已修复。
- 根因：finish 创建候选卡后仅追加 policy 分区，没有同步完整分区、来源、提醒与 plain_text/response。
- 修复：统一文档合并，按分区标识去重，保留相关分区与可读来源，重新渲染纯文本。
- 验收：测试覆盖每日安排、天气、来源、提醒以及重复合并；纯文本与 DTO 一致。

### BUG-2026-09-13-03：标准卡层次混乱，内部证据编号占用主要内容

- 严重性：中；状态：组件已实现，视觉 demo 待用户评审。
- 根因：通用“label/value/detail”布局对所有事实使用粗体，摘要与细项重复；来源直接拼 `src_...`；旧行程标准样式还会两行截断。
- 修复：新增共用 policy-card 组件。住宿/餐补作为费用区块，交通及核算使用规则行；只突出原文金额，不推算资格。完整条件保留，可读来源与说明展开查看。单独制度问答与行程内标准共用组件。
- 行程卡：会场/酒店地图优先，车次默认三条可展开；每日安排、关键差标、待确认项分区展示。修改会场仍生成新卡，旧卡不覆盖。

### BUG-2026-09-13-04：RAG 失败后依赖检查阻断规划，候选卡丢失

- 严重性：高；状态：当前分支已修复。
- 发现方式：本轮离线回归中模拟 RAG 不可用，得到 `DEPENDENCY_NOT_READY`，随后通用 fallback 丢掉 trip_options。
- 根因：不可用 RAG 结果被传作规划的可执行依赖；候选输出没有进入降级保留路径。
- 修复：只把 success/partial 结果作为依赖；制度缺失明确告诉规划角色，保留可用安排。保存当前版本候选输出，整轮超时仍保留地图、车次、酒店及已经核实的制度。
- 验收：RAG 失败及整轮超时分别有回归测试。

### BUG-2026-09-13-05：每日安排拼接后截断至 300 字

- 严重性：高；状态：当前分支已修复。
- 发现方式：真实模型验收第一天安排末尾为“【”，会场/住宿活动被截去。
- 根因：`render.py` 把 activities 合并到限长 value 并执行 `[:300]`，即使专业 Agent 返回了完整日程也丢失尾部。
- 修复：AnswerItem 增加完整 `activities` 数组；行程卡、通用卡与纯文本都读取该字段。规划 skill 同时要求日程不要重复整个车次库存表。
- 验收：超过 300 字的日程仍包含最后一项住宿安排。

### BUG-2026-09-13-06：完整查询中城市分类与住宿标准检索覆盖不稳定

- 严重性：高；状态：开放，未声称修复。
- 证据：本轮首次真实链路中，RAG 返回七项结论，但未取得重庆城市等级，住宿限额与餐补金额因此未知；历史独立城市标准测试曾取得重庆分类。
- 第二次真实链路：41.13 秒，12 项制度、2 天日程、12 个车次、4 家酒店、10 项来源；这次查到了重庆二类城市和餐补金额，但仍未取得二类城市住宿金额表。确认不是固定缺少城市字段，而是分类/住宿资料覆盖不稳定。
- 影响：流程和卡片传递完整，不代表政策内容已经覆盖完整；不能用 demo 金额或其他城市金额填补空缺。
- 当前处理：按 partial 交付，保留已核实条款，明确资料缺口；findings 上限由六项调至十二项，避免住房核算/凭证条款被结构限制挤掉。此调整不等于解决召回问题。
- 后续验收条件：用相同知识库版本固定评测城市等级、分档住宿、餐补三类命中情况，定位检索词、召回排序或回读选源问题后，再关闭此项。

### BUG-2026-09-13-07：静态页面更新但常驻 worker 未重载，修复未在聊天生效

- 严重性：高；状态：已修复并通过运行中的 HTTP 聊天接口验证。
- 用户现象：新卡片外观已更新，处理步骤依然只有保存行程和车次酒店查询。
- 运行证据：20:56:15 的请求 `31535c18-54e2-4a52-b27d-6f8cf4a608e3` 仍只有 trip_context、travel_info。容器从 14:15:47 启动，命令是 `uvicorn ... --workers 2`，没有 `--reload`。
- 根因：上一轮修改源文件、运行隔离测试后漏掉服务重载。静态文件从挂载目录立即更新；Python worker 的已导入模块继续运行旧逻辑。开发 compose 顶部注释错误声称已启用热更新，与实际 command 矛盾。
- 修复：确认没有进行中的执行后重启 hommey-app；两个 worker 于 20:59:20 启动，`/healthz` 返回 200。修正 compose 注释，明确多 worker 必须重启及正式 HTTP 验收要求。
- 正式验收：沿用用户这次 9月23日至24日北京→重庆、重庆大学科学城校区的已确认行程，通过运行中的 `/api/{user_id}/chat` 重新生成结果。新请求 `59b4386b-6a8f-4ef1-95e3-b73a5a8482e8`，HTTP 200，41.82 秒；实际包含 policy_rag、trip_planner，最终卡片含 9 项制度、2 天每日安排和会场地图。制度仍有待确认条件，因此整轮 partial，未声称全部完成。
- 本次验收会在用户原会话新增一轮更新后的行程回复；没有修改原始旧卡，也没有把旧请求当作新结果。
- 防回归交付要求：修改运行代码 → 确认活跃请求 → 重载实际 worker → 健康检查 → 正式 HTTP 请求 → 检查持久记录与卡片分区。新启动的测试 Python 进程通过不等于运行中的服务已生效。
