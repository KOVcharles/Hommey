# AgentRuntime 缺陷报告

日期：2026-09-10。范围：北京→南京表单提交及“继续”请求，以及本次修改中的回归缺陷。

现场请求：`a285fdb4-01f8-41e0-9b2b-3aab6499eb86`、`98a6c6cf-d50d-4a11-8e02-d15d70b6273a`。以下历史事实来自前一轮数据库检查点与服务日志；本轮没有改写这些请求。

## AR-001 / P0：只有摘要也能成为成功的行程结果

- 复现：提交“从北京出发，目的地：南京，2026-09-11出发，出差2天，出差目的：参加会议”。
- 实际：trip_context 返回 success，data 为空；apply_changes 报 EMPTY_CHANGESET 对应的文字错误；规划器随后认为五项全部缺失。
- 影响：用户填完表单仍不能规划，摘要中的“已整理”与实际状态不一致。
- 根因：所有角色共用宽松 Report，data 默认空字典；写入步骤依赖主模型自行调用。
- 修改：角色专用报告结构；行程字段及原文依据提前验证；合法行程由运行时通过原有原子回执写入，重复提交不再写库。
- 回归：`test_empty_trip_repaired_before_success_and_committed_without_model_apply`、`test_uncooperative_empty_trip_never_writes_and_report_repairs_are_bounded`。

## AR-002 / P0：漏引用被错误描述成未读取，诱发回读循环

- 实际：记忆和出行已经有 read_ids，report 却省略 evidence_refs；返回“请先回读来源”，反复读取同一份完整车次数据。
- 根因：引用字段可省略；缺引用和未读引用共用模糊错误信息。
- 修改：引用成为报告必填字段；事实 findings 携带逐项引用；区分 MISSING_EVIDENCE、UNREAD_EVIDENCE、UNKNOWN_EVIDENCE；错误提供 code、fields、next_action、retryable。
- 回归：角色 Schema 测试、`test_missing_reference_has_distinct_machine_error_even_after_read`。

## AR-003 / P0：局部失败被重复委派放大

- 实际：第一条请求三次启动类似 travel_info，44 次模型调用，主循环达到 14 轮后整轮失败，约 92 秒没有业务答案。
- 根因：只按工具调用 ID 幂等，没有任务与业务查询去重；失败提示只告诉模型交付，控制器没有收尾。
- 修改：查询指纹账本、并发重复抑制、已完成任务复用、相同失败任务禁止重跑；同版本每角色默认最多两项任务；三轮无进展收尾；两次报告错误终止子任务；默认 60 秒执行期限。
- 回归：重复读取、并发重复委派、改写任务绕过重试限制、模型断连、预算耗尽和期限取消测试。

## AR-004 / P1：“继续”丢失已完成结构化工作

- 实际：“继续”启动新请求，只接收上次摘要，又查记忆、政策、车次。
- 修改：checkpoint_version=2、work_items 和 control；明确“继续”时复用同会话、同版本、未过期且已提交的成功/部分结果。旧版检查点不直接升级为可信结果；未提交的历史变更不自动重放。
- 回归：`test_continue_restores_only_completed_results_and_does_not_requery_or_write`，过期、版本和丢弃结果过滤测试。

## AR-005 / P1：页面阶段与实际子任务不一致

- 实际：后台查询车次，页面仍为“分析中”。
- 根因：前端读取 event.intent，运行时没有发送该字段。
- 修改：进度事件携带 role 对应的 intent、display 和 task_id，前端优先使用 display。
- 回归：实际六角色运行事件断言；JavaScript 语法检查。

## AR-006 / P1：脱敏破坏检查点协议 ID（本轮发现）

- 证据：历史工具 ID 出现 `call_... [REDACTED:PHONE] ...`。
- 根因：随机十六进制 ID 内的连续数字被当成手机号，导致工具调用配对和来源引用不稳定。
- 修改：完整匹配的 call_/src_/result_ 协议 ID 保持原样；用户正文仍执行隐私脱敏。
- 回归：`test_checkpoint_redaction_preserves_protocol_pairs_and_still_redacts_personal_text`。

## AR-007 / P1：正常路径测试没有检查全部子任务状态（本轮发现）

- 复现：六角色测试只验证角色出现和最终卡片；memory 失败仍可能通过。
- 修改：断言全部角色均非 error/unavailable；追加真实模型与合成业务资料的完整请求测试，不把失败降级视为正常路径成功。
- 同时修正：复用 findings 校验时错误地把整个 MemoryData 当 PolicyData 校验，新增 preferences 字段被 extra=forbid 拒绝；改为仅校验 findings。

## AR-008 / 验证环境限制

- Docker Engine 当前未运行，无法执行容器内数据库与真实 RAG 联调。
- 本地 WebUI 测试在收集阶段初始化数据库，当前本地 DSN 被连接库判为格式无效，尚未执行到路由断言。
- 未输出或修改数据库凭据。此项是未完成的集成验证，不计为通过，不等同于上述控制器回归失败。

## AR-009 / P0：首次行程误用“替换已有行程”的授权门槛（真实模型复现）

- 复现：真实模型对首次填表选择 trip_action=new。运行时要求用户原文含“新行程/重新开始”，即使当前根本没有行程，也拒绝提交。
- 原始约束目的是防止模型擅自丢弃已有行程，错误地扩大到首次建立行程；仅修改提示词无法保证消除。
- 修改：空行程上的 new 由运行时规范化为 update；有现有行程时继续保留替换授权门槛，并返回 ACTION_NOT_AUTHORIZED 和明确字段路径。
- 同次发现：模型的 field_sources 已有 destination/duration_days，但 trip 丢失这两个值。现在以 MISSING_TRIP_FIELDS 拒绝，指向遗漏字段，不能把 summary 当成结构化事实。
- 回归：首次 new + 漏字段修复测试、禁止未经明确要求替换现有行程测试、真实模型表单请求测试。

## 验证结果

最终计数、真实模型结果及剩余边界见同目录 `2026-09-10-agent-runtime-control-report.md`。

## AR-010 / P1：完整表单仍依赖模型重新提取

- 真实模型多次在摘要/field_sources 中写出南京和两天，却遗漏 data.trip 中的对应值。
- 修改：对现有卡片的固定字段编码增加严格适配器，直接验证和保存；自由文本仍保留模型提取路径。模型断连时已提交字段不丢失。
- 对卡片已经提交的字段，重复 trip_context 委派直接复用结果。

## AR-011 / P1：报告错误没有具体违反的边界

- 真实模型 memory 报告因 findings 不符合数量/类型约束失败，旧错误仅提示 data.findings，无法知道如何修复。
- 修改：violations 返回字段、规则及允许的边界；不回显原始输入。记忆/出行查询增加强制阶段，不能查到最后一轮才开始汇报。
- 同时区分已有偏好读结果与新增偏好变更：重复已有值不会变成写操作。

## AR-012 / P1：超大观测可能使兜底检查点再次失败

- 修改前：大来源先进入 child.sources，然后保存检查点触发大小上限；之后降级保存仍携带大来源，可能再次超限。
- 修改：先检查单条与整轮新资料接收大小，再插入来源；返回 SOURCE_SIZE_LIMIT。新增超大来源注入测试，验证降级响应能够持久化。
- 边界：原始来源尚未全部外置，已有旧版巨型检查点仍需要独立迁移/清理策略。

## AR-013 / P1：规划已生成，主 Agent 仍不结束

- 真实模型已生成行程规划后继续 read_result，最终60秒期限交付了降级结果。
- 修改：表单任务以有效规划产物作为确定的交付条件，运行时直接完成；明确要求合规检查时保留后续检查。补齐漏传的当前版本政策/出行依赖，避免仅根据任务摘要规划。
- 纯事实整理/规划/合规角色只暴露 report，最多一次修复，不再先读指南消耗模型轮次。
- 回归：`test_form_plan_is_delivered_without_another_main_model_round`。

## AR-014 / 待持续评测：规划自由文本的语义一致性

- 一次真实模型测试生成“约3.5小时”的建议，而合成交通数据给出4小时；该次规划未传入交通依赖。
- 本版补齐遗漏依赖；类型及引用约束仍不能证明每一句自由文本都和证据完全一致。后续应进一步将交通活动绑定具体选项ID，并加入金额、时刻、职级适用性评测。本版不据此宣称达到生产发布标准。
- 最后一次通过的控制用例中，车次时长已按4小时输出，但规划活动把合成来源的“北京/南京”扩写成“北京南站/南京南站”。该语义问题仍未修复；控制用例通过只证明提交、终止及交付链路，不证明每项规划事实准确。

## AR-015 / P1：明确双意图缺少交付覆盖约束

- 核查：“给我查一下南京天气以及相关的差旅标准”不会命中原有整句制度快速路由；未复现正则截断。它原本交给主模型拆分，程序没有保证两个交付项都被处理。
- 修改：新增受限的整句组合入口，先登记两个步骤，并行查询、分别验收、统一结束；任一侧不可用时交付另一侧有效结果和降级说明。
- 验证：双侧成功、单侧失败、额外规划要求/否定/条件/多城市不误入快速入口，原文完整交回主 Agent。通用多意图覆盖仍是后续事项。

## AR-016 / P1：进度标签覆盖且终态不可恢复

- 修改前：并行角色覆盖同一个分析标签，结束删除处理指示器，done 不含 Runtime outcome/stop_reason，用户难以区分成功与部分失败。
- 修改：独立持久的公开计划组件，checkpoint 先存后发，done 携带终态；按用户和会话查询公开快照，重新打开会话时恢复。
- 验证：120 项离线回归中的状态与恢复用例，以及 Node DOM 合约测试。真实 HTTP 鉴权/数据库/浏览器集成尚未执行。

## AR-017 / P2：NDJSON 末尾错误可能被忽略

- 代码检查发现：循环内处理 error，但最后没有换行的 buffer 分支只处理状态、文档、chunk 和 done。
- 修改：末尾 error 使用同一错误抛出路径；公开计划与 done 在尾部也能接收。增加断连提示，不伪造执行终态。
- 验证：JavaScript 语法检查通过；该尾部错误分支尚未进行真实断流 HTTP 联调。

## AR-018 / P1：组合查询子任务仍继承整句请求，混淆缺项（真实模型复现）

- 首次真实模型测试中，天气查询已有天气证据，却把“差旅标准”列为自己的缺项。原因是 task 虽已限定天气，子上下文 request 仍包含两项要求。
- 修改：只在 Runtime 定义的组合快速入口中，将各步骤的受限请求文本传给对应子 Agent；完整用户原文仍由主 Runtime 保留用于权限和依据校验。
- 验证：第二次真实模型测试天气 succeeded，未再把制度列为天气缺项；离线测试断言两个子任务的 request 不包含对方查询要求。

## AR-019 / 开发中发现并修复：并行退出、恢复作用域与版本边界

- 新组合入口最初直接 await gather，异常退出可能留下兄弟任务。代码审查时改成显式任务列表加 finally 取消/回收，并加入超时与断连故障注入测试，验证活跃任务归零。
- 新恢复查询最初遗漏 stable_uuid 的 session 命名空间。接入审查发现后与 RunStore._key 保持一致，加入非 UUID 会话输入回归。
- 数据库 fencing 终态读取投影可能与恢复后事件的 revision 冲突。为投影预留中间 revision，并测试旧快照 < 停止投影 < 新所有者快照。
- 以上为本轮开发过程发现的问题，不称作已经发生的生产事故。

## AR-020 / 开发中发现并修复：恢复终态与缓存版本测试

- 取消状态直接复用到相同请求重试时，会被严格状态机拒绝重新开始。增加显式、最多一次的检查点恢复转换，保留 step_id；默认不开放模型驱动的任意重试。
- 更新 app.js 缓存版本后，一个旧测试因硬编码旧版本字符串失败（首次全套结果 117 passed / 1 failed）。调整为验证脚本只加载一次且新组件先于 app 加载，最终 120 passed。
- 这些修改不解决旧巨型 checkpoint 迁移或进程崩溃后的存活判断，相关限制仍保留。

## AR-021 / P2：卡片隐藏外侧图标后未保留 Hommey 标志

- 2026-09-11 截图及 CSS 核查确认：`.message-row.ai:has(.answer-card) .msg-avatar.ai` 隐藏外侧图标，标题区只有装饰线和品牌文字；不是 SVG 文件丢失。
- 修复：答案卡片、行程收集卡片标题区使用已有 Hommey SVG，亮/暗主题分别使用对应资源，更新浏览器缓存版本。
- 验证：真实浏览器预览中两种卡片图标均可见；填写字段和步骤切换正常。

## AR-022 / P1：已有行程结果反而阻止缺项收集卡片

- 请求 `e231cdfd-dffb-4e46-bf86-5879f90cc853` 已保存重庆，主 Agent 仍重复读取/提交，并在 finish(kind=ask) 时遗漏 question，最终 NO_PROGRESS。
- 原因：卡片由后续模型 finish 路径间接触发；finish 先验证提问字符串；fallback 又要求没有有效结果才返回表单。
- 修复：对明确的简单出差声明复用严格字段写入路径，提交后直接返回缺项表单；一般 finish 路径提前检查行程缺项，兜底允许已有行程结果生成卡片。组合查询不由简单声明入口截断。
- 验证：新增零模型调用、已有重庆不重复写、空提问恢复、旧 success 结果兜底、流式适配器卡片交付测试。

## AR-023 / P1：部分行程被报告为 success，缺项数组为空

- 实际结果只有 destination=重庆，模型却返回 success 和 missing_info=[]。摘要虽口头列出缺项，执行语义与真实字段状态不一致。
- 修复：Runtime 对有效行程提取结果按合并字段计算 planning_ready，不完整时规范为 needs_input，并生成缺项列表；保留取消行程的独立语义。
- 验证：注入模型假 success，确认状态变为 needs_input 且最终卡片为 waiting_input；本轮容器内全套 135 passed。详细运行与验证范围见 `2026-09-11-chongqing-intake-and-brand-fix.md`。
