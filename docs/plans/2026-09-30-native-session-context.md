# 原生会话上下文与 Agent 回答：简化改造方案

日期：2026-09-30。状态：完整设计方案；已按用户要求实施一个最小子集，详见 `docs/2026-09-30-minimal-context-change-report.md`。本文描述的完整原生消息存储、show_report、跨轮工具时间线等尚未全部实现。

2026-10-01 更新：原生 messages、跨轮主工具时间线、规则文件拆分及上下文快照已继续实现，当前落地范围见 [实施说明](../2026-10-01-native-context-implementation.md)。show_report、独立事件存储等仍未实施；下文保留原设计。

## 结论

以真实消息时间线作为模型上下文的主体：用户消息、主 Agent 工具调用、工具结果、主 Agent 最终回答。业务报告是工具结果，界面卡片是展示产物；下一轮延续消息时间线，不再从界面报告文字和报告目录重新拼出一份工作上下文。

主 Agent 使用自动工具选择，可以直接回答、追问，或调用工具继续工作。取消通用的强制 finish 出口，不增加固定的总结模型调用。现有业务写入、身份隔离、幂等和来源访问控制仍由运行时执行。

本方案借鉴 OpenClaw 的会话时间线、模型视图与持久记录分离、助手文字形成最终回复三个原则。下面的 JSON 和存储安排是 Hommey 的设计建议，不是 OpenClaw 的原样实现。

## 已确认的现状

- 样本：`tmp/debug/latest-hommey-turn-20260928-163843/model-inputs-reconstructed.json`。
- 第一次模型调用有 9 条消息，第二次有 11 条；第二次的前 9 条与第一次逐项相同。
- 历史 assistant 中已有 1,052 字符的南京、上海报告。随后 read_result 返回 1,927 字符；其 summary、全部五条 conclusion 和全部 missing_info 都已经出现在历史回答里。
- 最后回答与上一轮回答逐字相同。finish 只能选择整份报告，不能形成面向追问的回答。
- 当前保存模型消息时忽略 ModelReply.text，assistant_message 固定写 content=None。
- 新用户轮只继承报告对象，重新加载界面问答，没有延续上一轮主 Agent 的完整工具消息。
- compact_tool_history 直接修改 checkpoint 中的 messages。日志是最终检查点加导出时代码的重建结果，并非逐次请求快照。

OpenClaw 同样会在普通请求中携带必要历史，工具结果和最终回答也可能存在合理的内容重合。优化目标是取消人为重复包装及不必要的回读，而不是要求所有事实只能出现一次，或承诺每次请求只发送新增消息。

## 模型输入

只保留三个部分：稳定的规则和工具定义、少量当前业务环境、原生 messages。不要再建立包含 conversation/work/reference_results 的大 user JSON。

组装函数的职责可以表示为：

```python
def build_context(rules, environment, history, current):
    messages = project_for_model(history + current)
    messages = prune_to_budget(messages)  # 只修改副本，保留消息与工具配对
    return provider_messages(rules, environment, messages)
```

environment 只在有值且影响当前工作时包含 today、trip 等业务字段。用户、会话、请求标识及工具执行账本由宿主维护，不要求模型复述。环境数据由 provider 适配层以明确标记的数据区注入，不伪装为用户的新请求，也不把数据库中的自由文本升级为系统指令。

单轮内固定环境快照，变更通过实际工具结果传入；不在每个工具轮次重写前面的 work 目录。下一用户轮再刷新环境，尽量保持历史前缀稳定。

历史主线为：

```text
user：查南京和上海的标准
assistant：delegate(policy_rag, 具体任务)
tool：有来源的简洁报告
assistant：围绕问题给出的最终回答
user：两个地方都是这个标准吗？
```

这里的 delegate/tool 必须是真实执行记录，不能由历史报告伪造。子 Agent 内部的检索与回读过程留在子任务记录中，不全部复制到主会话。

## 报告的模型视图

运行时继续保留完整报告及来源。工具只返回模型决策所需的视图，推荐通用骨架为 id、content、sources；错误、时间或其他信息按业务必要性出现，不输出一组默认 false/null。

下面是结构示意，不是重新核验的政策结论：

```json
{
  "id": "result_example",
  "content": "科研经费：在相同人员类别下，两地适用本资料列出的统一标准。[s1]\n非科研经费：两地住宿具体金额尚未取得，不能确认相同。[s2]",
  "sources": {
    "s1": "来源标题，第11页",
    "s2": "来源标题，第12页"
  }
}
```

真实运行使用可回读的真实来源 ID；这里的短 ID 仅为示意。content 可以是文字，也可以是车次、天气等任务所需的紧凑对象，不把所有业务硬压成文字。保留适用条件、例外、未知项和必要的查询日期；检索日期与政策生效日期分别表达，不相互替代。

不重复发送 role/task（调用参数已经包含）、input_version（运行时校验使用）、sources 原始 metadata、完整 UI 文档，也不在 summary 和 findings 中各写一遍相同事实。存储 schema 和模型视图由一个函数转换，避免为了模型字段精简改坏业务持久化。

read_result 继续提供按 ID 回读能力，返回同样的报告视图。它用于报告已离开上下文、经过压缩或用户指定较早资料等情况；不增加“读过则禁止再读”的 gate。已在消息中的报告不另行挂一份全量目录。更早结果通过现有历史查询能力定位后读取，必要时扩展其同会话报告查询，而不新增一个检索 Agent。

read_source 返回 id、正文和必要出处；路径、分块流水号和解析器配置留在后台。保留分页能力。

## 最终回答与界面展示

主 Agent 使用 tool_choice=auto；子 Agent 的结构化 report 阶段仍可按其契约强制工具输出。主循环保留 ModelReply.text：有工具调用时作为该 assistant 消息的文字，无工具调用且有最终文字时正常结束本轮。空白、失败、取消及未结算工具继续按协议处理。

普通确认、解释、追问和拒绝使用自然语言，不再通过 finish.kind 分类后套模板。取消 result_ids 必填及 reuse_reasons 修复循环。不要默认附带全部已读报告。

确实需要完整报告或结构化卡片时，用一个明确展示动作替代通用 finish，例如：

```json
{"result_id": "result_example"}
```

工具名可为 show_report。宿主按 ID 渲染已有结构化产物，工具消息只返回简短展示回执，主 Agent 仍可说明结果。该动作是展示能力，不是普通文字回答的前置条件。已有行程表单和候选方案工具继续负责其界面产物，不把完整卡片 DTO 再复制进模型历史。

模型负责组织有据答案后，schema 无法确定性证明每句话的正确性。事实质量通过清楚的来源、适用条件、时效信息和多轮评测检验；不再用新增一段理由字符串来代替这一问题。实际业务写入的权限、用户原文依据和提交回执保持运行时控制。

## 存储和历史组装

先复用 supervisor_runs.checkpoint.main.messages 存当前用户轮的原生消息增量，包括本轮最终助手文字。不要将全部历史或 system prompt 嵌套保存进每轮 messages。checkpoint 的其他字段继续服务恢复和业务执行；conversation_messages 继续保存用户界面问答及卡片。

历史加载按会话内用户消息顺序和 request_id 关联 supervisor_runs：有新格式主会话消息时使用该段，没有时回退到界面 user/assistant。绝不把同一轮的两种表示同时拼进模型输入。当前轮从历史查询中排除，由 current 单独追加。中断轮保留合法的已结算消息，不回放未执行工具，也不把孤立工具消息拼入输入。

不能直接把多个原生工具消息塞进现有 conversation_messages：该表和 append_message 按 user_id/request_id/role 幂等，一轮多个 assistant/tool 会发生冲突。使用每轮已有 checkpoint 的消息数组可以先避免修改这个表。

旧记录只做读取适配，不改写、不伪造工具轨迹。不承诺从旧 checkpoint 恢复出缺失的原始文本。新消息和旧格式的分界在统一适配入口处理。

完整报告仍由后台结果存储提供。read_result 按当前用户、会话及有效保留期查找所属记录，不能因为报告退出提示词就不可访问；过期或删除的记录不能通过历史回读绕过生命周期。原始工具轨迹保留至既有保留期，不把它等同于永久存储或 provider HTTP 原文。

## 上下文增长

短会话直接延续真实消息，不做逐轮语义去重、相关性分类和自动摘要。普通工具循环追加消息，允许模型正常回读，避免为了省少量字符频繁改写缓存前缀。

接近预算时，先在模型视图中缩减较早的大工具结果，保留 ID、必要说明和成对消息；当前请求、近期问答和刚返回的工具结果保持完整。用模型 token 预算并预留输出空间，字符数只作为诊断或保守后备。

长会话仍超预算时，再接入现有会话摘要存储，保留用户约束、未解决问题及来源 ID，并保留近期完整消息。摘要是派生记录，不替换原始历史。此项可以后续接入，不是修复当前短会话重复的前置条件。

## 代码改动边界

| 位置 | 改动 |
|---|---|
| context_window.py | 原生消息组装；历史按轮选择单一表示；压缩只作用于副本 |
| services.py / store.py | 同会话按顺序加载消息段；按 ID 回读完整存档；保留用户和生命周期边界 |
| model_client.py | 主循环允许 auto；保留工具调用伴随文字及最终文字 |
| engine.py | 分离加载的 history 与本轮 current；自然语言终止；不再解析 messages[1] 获取业务状态 |
| engine.py 的直接路由 | 统一普通自然语言请求进入主循环，避免 direct_policy/direct_queries 绕过答案组织；显式表单提交仍保留专用路径 |
| 子任务上下文 | task、必要事实及显式依赖；取消机械复制整段历史，具体任务及限制由主 Agent 委派 |
| contracts.py / profiles.py | 去除通用 finish 和 reuse_reasons；工具说明保留操作意义，删除大段补救规则 |
| render.py | 普通文字直接交付；结构化报告按明确展示动作渲染 |

不是只改 prompt，也不需要引入新框架。先把同一主消息链、主模型自然回答、报告轻量视图和只读投影一并打通；不要先保留旧交付路径再叠一套答案状态机。

## 验收

1. 结构回归：新一轮继承真实主工具消息及最终文字；同一轮不重复拼入 UI 报告；当前用户消息一次；调用与结果正确配对。
2. 恢复回归：已有工具不重跑，业务写入不重复；压缩不改变持久记录；用户、会话、删除、过期隔离有效。
3. 样本评测：对“两地都是这个标准吗”回答共同部分和尚未知的差异，不原样重播旧报告；有足够证据时可一次主模型调用完成，不能把“一次”作为所有情况的硬限制。
4. 反例：用户质疑原文、变更经费来源、要求完整报告、引用窗口外历史、询问实时余票时，Agent 仍能自主选择回读、重查或展示。
5. 指标：实际请求 token、主模型轮数、重复回读次数、当前问题覆盖、错误事实；不只看 JSON 校验通过率。

当前方案尚未执行新架构的在线评测，不宣称已经获得延迟、token 或正确率提升。
