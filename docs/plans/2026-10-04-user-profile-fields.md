# 重庆大学报销用户资料字段方案

日期：2026-10-04。字段依据及实现说明。已接入可跳过的首次资料初始化、设置编辑、按用户隔离的 JSON 存储和 Agent 投影；示例文件仅展示结构，不是某位用户的真实配置。

## 依据与范围

当前 `.env` 的 `HOMMEY_RAG_SEARCH_SCOPES=cqu/finance`，该目录只有《重庆大学财务报销指南（2025年4月）》PDF。原企业演示制度不参与此次字段判断。

源文件：`data/documents/cqu/finance/重庆大学财务报销指南-2025年版.pdf`。以下页码为文档印刷页码；物理 PDF 页码为印刷页码加 4。

| 指南内容 | 页码 | 对字段的影响 |
| --- | --- | --- |
| 报销封面需经办人、项目负责人、二级单位签字；科研项目填报人与负责人一致时有例外 | 2 | 记录单位及用户在具体项目中的角色；每次实际填报人仍需确认 |
| 专家咨询及讲座按专业技术职称、院士/全国知名专家等条件区分 | 4 | 职称层级和特殊专家身份分别保存；实际收款人可能不是当前用户 |
| 答辩费区分校内、校外人员 | 5 | 默认人员类别有用途，但经办人身份不能替代专家身份 |
| 科研经费包含纵向、横向；指南列出学校项目代码位置规则 | 6 | 常用经费支持科研/非科研、纵向/横向及可选财务项目代码 |
| 科研差旅交通/住宿按职称、职员等级、二级正高、55岁条件区分 | 6-7 | 职称层级、专业技术岗位等级、职员等级分开；出生日期选填 |
| 非科研差旅采用另一套交通/住宿及补助条件 | 8 | 每次业务要能覆盖默认经费，不能把经费类别固定为用户身份 |
| 国际差旅区分教职工/学生和行政级别 | 9 | 人员类别常驻；行政级别可选扩展 |
| 工作用餐对财政拨款有限制；军工项目转拨需特定审批 | 11 | 经费来源与科研类别是两个维度；军工标记属于项目 |
| 公务卡结算、预借款条件 | 14 | 可选保存是否持有公务卡；实际支付方式仍属于单次事项 |
| 外籍来访人员要求、图书资产与不同经费类别 | 17 | 国籍可选扩展；来访审批、图书采购条件不存为长期身份 |
| 国家科技计划与国家社科基金项目的版面费要求不同 | 18 | 项目计划类别需单独保存，不能仅用“科研经费”概括 |

学号、工号、性别是用户明确提出的账户资料需求。在此指南中未找到将它们作为报销标准分档条件的明确依据；不能称为指南要求注册必填的字段。

## 建议的保存结构

完整示例见 [JSON 示例](2026-10-04-user-profile-fields.example.json)。实际新用户的 `funding.projects` 应为空数组；示例中的 `example-project` 只展示一条项目记录的字段，不创建空白项目。所有未知值用 `null`；未知布尔值不填 `false`。

已有平台 `user_id`、邮箱和权限角色仍由鉴权系统维护，不在用户可编辑资料中重复保存。个人资料中的职员等级不改变平台的 user/admin 权限。

### 基本资料 `basic_info`

| 字段 | 类型 | 设置入口与用途 | 模型默认可见性 |
| --- | --- | --- | --- |
| `real_name` | string/null | 姓名，选填；默认可使用现有显示名称 | 称呼需要时提供显示名称 |
| `institution` | string/null | 所属机构；当前部署可展示重庆大学。变更机构不自动变更知识访问范围 | 常驻 |
| `department` | string/null | 学院/二级单位，选填；辅助说明材料与签章路径 | 必要时 |
| `personnel_category` | enum/null | 默认身份：教职工、学生、校外人员、其他；“暂不确定”为 null | 常驻 |
| `employee_number` | string/null | 工号，选填；使用字符串保留前导零 | 默认不注入 |
| `student_number` | string/null | 学号，选填；学生表单显示学号，教职工表单显示工号 | 默认不注入 |
| `gender` | enum/null | 性别，选填；男、女、其他、不愿透露，未填写为 null | 默认不注入 |
| `birth_date` | ISO date/null | 出生日期，选填；支持年龄条件判断 | 默认不注入完整生日；按相关业务日期提供派生年龄 |
| `nationality` | string/null | 国籍，可在更多资料中选填 | 涉及外籍本人等条件时 |

`personnel_category` 是默认本人身份。代他人报销、专家酬金、同行人问题应读取当前事项的实际主体，不能套用账户用户的身份。双重身份用户可在本次事项中指定按哪种身份讨论；当前设置表单按选择的人员类别显示对应编号。

### 报销身份 `policy_identity`

| 字段 | 类型 | 含义与填写建议 |
| --- | --- | --- |
| `professional_title_level` | enum/null | 专业技术职称层级：正高、副高、中级、初级、无；未确定为 null |
| `professional_position_grade` | integer/null | 专业技术岗位等级，单独记录“二级正高”等情况；不知道时不填写 |
| `staff_grade` | integer/null | 职员等级，例如二级、三级、四级；与技术岗位等级分开 |
| `administrative_rank` | enum/null | 行政级别，国际差旅等需要时补充；省部级、司局级、其他，未知为 null |
| `academician_status` | enum/null | 院士、经明确确认的相当院士人员、非上述身份；未知为 null |
| `nationally_recognized_expert` | boolean/null | 全国知名专家，专家劳酬场景的可选身份；不能因此自动采用院士差旅标准 |

首期表单展示职称层级、技术岗位等级和职员等级；行政级别与特殊身份折叠到“更多报销身份”。学生无需填写不适用的职称/等级。明确“不适用”和“尚未填写”在 UI 中可区分，后台未知值仍保持 null；必要时使用人员类别解释不适用。

生日与业务日期共同决定年龄，不能长期保存一个固定 `age` 或永久的 `over_55` 开关。指南交通条款使用“55周岁以上”，住宿条款使用“55周岁及以上”；临界情形按检索到的具体条款解释，不用一个派生开关抹平差异。指南未明确年龄判定基准日时保留待确认。

### 常用经费 `funding`

采用项目列表和 `default_project_id`。同一个人可能在不同事项中使用不同经费，默认项目只减少重复选择。

| 项目字段 | 类型 | 含义与填写建议 |
| --- | --- | --- |
| `id` | application-generated string | 应用内部引用 ID，不要求填写经费号才能新增项目；接口未提供 ID 时由服务端生成 |
| `name` | string/null | 用户可识别的项目名称/简称 |
| `financial_project_code` | string/null | 学校经费号/财务项目代码，选填；界面标注“经费号（财务项目号）” |
| `funding_category` | enum/null | 科研经费或非科研经费；不确定为 null |
| `research_type` | enum/null | 科研项目的纵向/横向；非科研项目不适用 |
| `program_type` | enum/null | 国家科技计划、国家社会科学基金、其他；未知为 null |
| `funding_source` | enum/null | 财政拨款或非财政拨款；未知为 null，与科研/非科研独立 |
| `is_military_project` | boolean/null | 是否军工项目，可选展开 |
| `user_project_role` | enum/null | 本人在此项目中的角色：负责人、成员、经办人；未知为 null |

经费号/财务项目代码与国家基金批准号不是同一种编号。首期只提供经费号；以后需要科研立项号/批准号时再增加独立 `grant_number`，不重复存同一个编号。

指南第 6 页的项目代码规则只提供科研经费分类依据，不能据此确认项目归属、国家基金计划类别、用户权限或完整报销资格。若用户填写的科研类别与按指南得到的代码分类冲突，应展示待核对状态，不能静默覆盖。分类依据保留来源、版本和日期；金额与审批规则继续从 RAG 获取。

科研/非科研、纵向/横向、计划类别、财政来源不能压成一个互斥下拉框。仅有“纵向项目”不能推出是国家科技计划或国家社科基金；其他国家基金也不能未经依据自动归入国家科技计划。

`user_project_role` 不等于当前报销单的实际填报人。涉及第 2 页签字例外时仍核对本次主体与项目负责人是否一致。

### 其他已有资料

- `settlement.has_official_card`：是否持有公务卡，选填。实际是否使用公务卡支付、支付日期及交易记录留在单次事项。
- `travel_preferences`：沿用当前常驻地、交通、酒店、航司、座位、饮食和预算偏好。偏好不产生制度资格，商务座偏好不能代替允许乘坐商务座的条件。
- 元数据：接口返回 `updated_at`、`revision`、`onboarding_status`；模型投影使用 `verification=user_entered`。用户设置填写属于用户声明，不能标成学校系统核验。客户端不能修改元数据。

不把身份证号、银行卡号、护照号作为首期资料字段；现有能力是制度咨询与材料建议，其具体凭证留在实际业务材料中。

## 持久资料与 Agent 上下文的连接

保存的完整用户资料和模型可见投影分别处理。主 Agent 沿用现有 `user_profile.defaults`、`user_profile.preferences`，新增投影字段 `identity`、`funding`、`settlement`；`funding` 完整包含 `default_project_id` 与所有 `projects`，每个项目保留稳定 ID、名称、经费号、类别、科研类型、计划类别、来源、军工属性与本人角色，不截断项目列表。`default_funding` 保留为同一默认项目的兼容摘要。无需为了获取这些已经保存的字段再调用记忆查询工具。差旅偏好继续使用原有存储，不在新的 JSON 表中重复保存。

模型投影包含：机构、默认人员类别、相关职称/等级、相关业务日期上的派生年龄，以及全部常用项目的经费属性和选填的经费号，即使没有选择默认项目也提供完整列表。经费号可用于结合指南核对分类，不能确认归属或权限。未知字段保持 `null`，明确的否保持 `false`。默认不注入学号、工号、性别和完整生日。

角色分配：

| 角色 | 提供的资料 |
| --- | --- |
| 主 Agent | 本人机构、默认人员类别、适用的身份条件、全部经费项目及默认标记、原有差旅默认值和偏好 |
| policy_rag / compliance | 本人相关身份、全部常用经费项目及默认标记，按本次实际项目判断 |
| trip_planner | 规划需要的身份、全部常用经费项目、出发地和相关偏好 |
| trip_context | 出发地默认值及本次行程需要的资料 |
| travel_info | 城市及出行偏好；普通天气/POI 查询无须个人编号或经费 |
| memory | 按现有权限处理已授权记忆事项；不因此获得任意读取完整账户资料的权限 |

每个新请求从当前用户资料存储读取一次，下一请求刷新；同一请求恢复沿用 checkpoint。资料以用户隔离的 PostgreSQL JSONB 长期保存，跨会话保留。修改差旅偏好不丢失任何经费项目。当前明确指定的本人条件、实际业务主体和当前经费覆盖默认值；按项目 ID、经费号或名称匹配，不混用不同项目的属性，只有影响任务的项目歧义才补问。一次临时覆盖不修改长期资料，常用经费通过个人信息保存。

项目余额、预算额度、核定报销限额、票据状态、审批通过状态、付款方式、会议是否包食宿、论文类别/与项目的关联、出访批件等都留在当前业务/外部权威记录中，不作为用户可编辑的长期事实。本人资料不能代替收款专家、同行人员或其他申请人的资料。

## 设置与注册流程

保留现有设置窗口的视觉层次，在“个人信息”卡片内提供：

1. 基本资料：姓名、学院/单位、默认人员类别、学号、工号、性别；生日/国籍放到更多资料。
2. 报销身份：职称层级、技术岗位等级、职员等级；更多身份折叠。
3. 常用经费：项目列表、默认项目、新增/编辑/删除；经费号明确标为选填。
4. 差旅偏好：沿用现有条目。
5. 当前出差任务：沿用现有条目。

一级窗口显示摘要行，例如“基本资料 · 未完善”“报销身份 · 副高”“常用经费 · 2 个项目”，点击后进入编辑子页。二级编辑页面可关闭取消编辑和保存，保存成功后更新摘要；不在主窗口堆叠整张长表单。

常用经费子页中，已保存项目默认显示摘要卡片：项目名称、类别/来源/选填经费号、默认选择及“展开编辑”。新增项目直接展开；点击“完成编辑”或“收起”平滑折叠并更新摘要，草稿保持不丢失。只有页面底部“保存资料”或“完成设置”提交全部项目到长期存储，关闭取消不会提交草稿。展开状态只属于界面，不写入用户 JSON。

注册后的首次进入聊天会出现独立资料初始化步骤：先选择本人类别与所属单位，再按需填写学号/工号和性别；经费与高级身份放在后续可选部分。所有资料环节可以跳过，后续在设置中补充，避免阻塞首次提问。学生显示学号、教职工显示工号。切换类别时在草稿中清除不适用的身份和编号，保存前不会修改数据库。已有账户尚未初始化时也显示一次，跳过状态会保存。

Agent 不在普通聊天开场索要性别或学号/工号。只在实际问题依赖缺失的人员/经费条件时补问必要条件，并说明可在设置保存为默认资料；本次问答补充不自动写入长期档案。

## 实现位置与验证

`core/user_profile.py` 校验字段及人员/经费关系，`context/user_profile_repository.py` 保存 JSONB 并使用版本号防止并发覆盖，`webui_new/routes/personal_profile.py` 提供 GET/PUT `/api/{user_id}/profile` 及 POST `/skip`。迁移为 `0026_user_personal_profiles.sql`，服务启动自动执行。`personal-profile.js/css` 提供分步初始化及编辑界面；`agent_runtime/user_profile.py` 生成角色投影。数据库访问通过当前登录用户绑定，不能接受另一个用户 ID 来覆盖资料。

验证覆盖可选字段、未知值、前导零、多项目默认选择、角色投影、跨用户隔离、初始化跳过、设置保存/恢复、失败保留草稿、版本冲突和手机/深色显示。真实 PostgreSQL 检查使用连接内临时表，不改动用户资料。原有差旅偏好上下文和会话导航回归检查继续保留。
