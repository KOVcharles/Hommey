# 快速差旅结构化入口改造设计

> 日期：2026-08-25<br>
> 状态：待实施<br>
> 适用主链路：`itinerary_planning` intent → `plan-trip` Workflow

## 1. 背景

当前用户可以通过自然语言发起差旅规划；信息不足时，系统运行
`event_collection` 并展示行程补全卡。该方式适合自由表达和少量补充，但当用户希望一次性
创建完整差旅时，逐轮输入出发地、目的地、日期、时长、目的和会议地点，操作成本较高。

同时，目的城市与具体会议地点的精度要求不同：

- 目的城市用于政策、天气、车次和城市级规划，只需确认到行政区；
- 会议或客户地点用于附近酒店推荐，需要确认到具体 POI 或可解析地址；
- 楼栋、楼层和会议室可能不是公开 POI，应作为地点说明保存，不能要求地图服务完整收录。

因此新增“快速差旅”前端入口，让用户主要通过选择器、日期控件和常用标签一次补齐信息，
然后直接进入现有 `plan-trip` Workflow。

## 2. 核心决策

“快速差旅”仅是现有差旅规划流程的结构化输入方式，不是新的业务流程。

```text
快速差旅前端表单
    │
    │ 结构化 trip_input
    ▼
现有 itinerary_planning Goal
    ▼
现有 plan-trip Workflow
    ├─ event_collection
    ├─ rag_knowledge
    ├─ information_query
    ├─ train_query
    ├─ itinerary_planning
    └─ trip_compliance
```

不得新增以下概念：

- `quick_trip` intent；
- `quick_trip` Goal；
- QuickTrip Workflow 或 QuickTrip Agent；
- 独立的 Run、Turn、状态表或恢复机制；
- 第二套行程字段校验、记忆回写或答案合成逻辑。

`quick_trip_form` 只允许作为输入来源标识，用于前端展示、审计和指标统计，不参与意图授权、
Goal 身份或状态推导。

## 3. 目标与非目标

### 3.1 目标

1. 用户主要通过选择完成一份可规划的差旅信息，减少逐字段对话。
2. 完整提交后直接执行现有 `plan-trip` Workflow。
3. 缺失或冲突时使用现有 `WAITING_USER`、`TripIntakeDocument` 和续跑逻辑。
4. 出发地、目的地和会议地点可保存为经过确认的结构化地点。
5. 会议地点明确时，可在现有外部信息节点中查询并推荐附近酒店。
6. 自然语言入口、补全卡入口和快速差旅入口共享同一事实源和状态机。

### 3.2 非目标

- 不在 Web 页面复刻高德导航；
- 不展示逐路段精确路线；
- 不提供酒店预订、付款或取消；
- 不把地图 POI 参考消费当作实时房价或可订库存；
- 不让地图服务决定 `planning_ready`、合规结论或工作流状态；
- 不以快速差旅替换原有聊天和行程补全卡。

## 4. 用户入口与交互

### 4.1 入口位置

在首页欢迎区和聊天输入框工具区增加“快速差旅”按钮。桌面端打开侧边抽屉，移动端打开底部
面板，不跳离当前会话。

仅打开或关闭表单时不创建 Run、不写 `active_trip`、不持久化用户消息。用户正式提交后才进入
现有请求链路。

### 4.2 表单布局

```text
┌─ 快速差旅 ───────────────────────────┐
│ 出发地      [使用常驻地：上海       ▼] │
│ 目的地      [搜索并选择城市         ▼] │
│ 出发/返程   [2026-08-28] [2026-08-30] │
│ 出差目的    [客户拜访] [会议] [培训]  │
│ 会议地点    [搜索并选择具体地点      🔍] │
│ 地点说明    [3号楼 3层 301会议室]      │
│ 工作时间    [09:00] 至 [17:00]         │
│                                        │
│ ☑ 推荐会议地点附近酒店                 │
│ ☑ 查询天气  ☑ 查询高铁                 │
│                                        │
│              [生成差旅方案]            │
└────────────────────────────────────────┘
```

### 4.3 字段与控件

| 字段 | 是否必填 | 控件 | 默认或快捷来源 |
| --- | --- | --- | --- |
| 出发地 `origin` | 是 | 城市/地点下拉选择 | 已确认常驻地、公司地点、近期出发地 |
| 目的地 `destination` | 是 | 城市/行政区下拉选择 | 近期目的地 |
| 出发日期 `start_date` | 是 | 日期选择器 | 无 |
| 返程日期或时长 | 是 | 返程日期选择器 | 自动计算 `duration_days` |
| 出差目的 `trip_purpose` | 是 | 常用标签，其他可补充 | 客户拜访、会议、培训 |
| 会议地点 `work_location` | 条件必填 | POI/地址下拉选择 | 近期工作地点 |
| 地点说明 | 否 | 短文本 | 楼栋、楼层、会议室 |
| 工作时间 | 否 | 时间选择器 | 常用工作时间 |
| 推荐附近酒店 | 否 | 开关 | 默认开启 |
| 天气、车次等能力 | 否 | 开关 | 沿用 Workflow 默认能力 |

当“推荐附近酒店”开启时，会议地点必须有经过确认的 POI 或地址坐标；关闭时允许会议地点暂未
确定，基础差旅规划仍可继续。

### 4.4 减少输入

- 出发地优先显示已确认的 `home_location`，但仍要求用户本次确认；
- 展示近期使用的目的城市和会议地点快捷项；
- 出差目的提供常用标签；
- 返程日期选择后自动计算天数；
- 已存在有效行程 Run 时，表单预填该 Goal 已确认的数据；
- 任何由偏好或历史生成的值都标注来源，不能静默成为本次已确认事实。

## 5. 地点选择设计

### 5.1 城市与具体地点分离

`destination` 保存城市或行政区，用于政策、天气、车次和规划范围；`work_location` 保存具体
会议或客户地点，用于酒店搜索。附近酒店不得默认以整个目的城市的中心点作为推荐锚点。

示例：

```json
{
  "destination": "杭州市",
  "destination_place": {
    "name": "杭州市",
    "adcode": "330100",
    "level": "city",
    "verified": true,
    "source": "amap"
  },
  "work_location": "阿里巴巴西溪园区",
  "work_location_place": {
    "poi_id": "B0XXXXXX",
    "name": "阿里巴巴西溪园区",
    "address": "杭州市余杭区文一西路969号",
    "adcode": "330110",
    "citycode": "0571",
    "location": {"lng": 120.027, "lat": 30.279},
    "verified": true,
    "source": "amap"
  },
  "work_location_note": "访客中心3楼301会议室"
}
```

### 5.2 强制选择候选

地点控件分别维护：

```text
input_text      用户当前看到和编辑的文字
selected_place  用户从候选列表中确认的结构化地点
```

规则：

1. 用户输入文字只触发候选搜索，不代表地点已确认；
2. 只有选择候选后 `selected_place` 才有效；
3. 选中后再次编辑文字，立即清空旧 `selected_place`；
4. 严格字段未选候选时，不允许提交；
5. 下拉项展示名称、区县、地址和地点类型，降低重名误选；
6. 后端使用 POI ID 或地址结果重新校验，不能信任浏览器提交的任意坐标。

### 5.3 无候选时的降级

1. 在已选目的城市内扩大搜索关键词；
2. 自动移除楼层、房间号等地图服务通常不收录的细节；
3. 允许选择园区、写字楼或附近地标作为地理锚点；
4. 楼栋、楼层和会议室保存到 `work_location_note`；
5. 完整地址可尝试地理编码后作为地址候选供用户确认；
6. 仍无法确认时不得伪造坐标，允许用户关闭附近酒店推荐并继续基础规划。

## 6. 输入契约

快速差旅提交应复用现有聊天/Workflow 请求入口，只增加可选的结构化 `trip_input`，不建立新的
业务 API 或状态入口。地点搜索可以使用独立的无状态查询 API，但它只返回候选，不创建任务。

示例请求：

```json
{
  "message": "生成本次公司差旅方案",
  "input_source": "quick_trip_form",
  "trip_input": {
    "origin": "上海市",
    "destination": "杭州市",
    "start_date": "2026-08-28",
    "end_date": "2026-08-30",
    "duration_days": 3,
    "trip_purpose": "客户拜访",
    "work_location": "阿里巴巴西溪园区",
    "work_location_note": "访客中心3楼301会议室",
    "origin_place": {},
    "destination_place": {},
    "work_location_place": {}
  },
  "capability_selection": {
    "weather": true,
    "train": true,
    "nearby_hotels": true
  }
}
```

约束：

- `input_source` 仅表示来源；
- 服务端将该请求映射到标准 `itinerary_planning`；
- `trip_input` 注入现有 scoped task context，最终仍由 `event_collection` 校验和合并；
- 前端不得直接设置 `planning_ready`、Goal 状态或 Node 状态；
- 服务端保存一条适合阅读的用户消息，同时将结构化数据作为消息元数据或请求上下文持久化；
- API 重放继续使用现有 `request_id` 幂等机制。

## 7. 与状态机的关系

### 7.1 当前会话没有活动 Run

提交后创建标准 `itinerary_planning` Run、Turn、Goal 和现有 Workflow Nodes。快速差旅本身没有
状态身份。

### 7.2 当前存在等待中的行程规划

表单读取当前 `focused_goal_id` 对应的已确认字段；提交后新建 Turn，恢复同一个 Run 和同一个
`itinerary_planning` Goal。不得追加一个新的快速差旅 Goal。

### 7.3 信息完整

```text
提交 trip_input
→ event_collection 合并并校验
→ planning_ready=true
→ 不暂停
→ 继续原 plan-trip 后续 Nodes
→ Composer 生成完整答案
```

### 7.4 信息不完整或冲突

```text
提交 trip_input
→ event_collection 发现 missing/invalid/conflict
→ planning_ready=false
→ 使用现有 WAITING_USER
→ 输出现有 TripIntakeDocument
→ 用户补充后恢复同一个 Goal
```

### 7.5 用户取消或中断

取消当前行程、停止本轮执行和继续任务均沿用现有 Run/Turn 生命周期。快速差旅表单不维护独立的
取消、过期或恢复状态。

## 8. 附近酒店能力

### 8.1 Workflow 归属

附近酒店查询属于现有 `plan-trip` Workflow 的外部信息能力，建议作为 `information_query` 的
`nearby_hotels` capability，而不是新 Workflow：

```text
information_query Node
├─ weather
├─ local_transport
└─ nearby_hotels
```

只有 `work_location_place.verified=true` 且存在坐标时执行酒店周边搜索。外部服务失败时按
`on_failure: continue` 降级，不使整个行程规划失败。

### 8.2 酒店展示字段

- 名称、地址、行政区、商圈；
- 距会议地点的直线距离；
- 类型、电话、评分；
- 可用时展示图片和参考消费；
- 推荐原因；
- 数据来源和查询时间；
- “在高德中打开”链接。

地图 POI 的参考消费不是指定日期实时房价，也不代表库存、早餐、房型、取消政策或公司协议价。
没有可靠实时价格时，不得给出“住宿费用确定合规”的结论，应显示“价格与可订状态待差旅平台
确认”。

### 8.3 推荐排序

建议先过滤明显不相关的 POI，再按以下因素解释性排序：

| 因素 | 初始建议权重 |
| --- | ---: |
| 距会议地点距离 | 35% |
| 公司住宿标准适配度 | 25% |
| 酒店评分 | 15% |
| 用户酒店品牌偏好 | 15% |
| 商圈和交通便利度 | 10% |

若缺少实时价格，住宿标准项只能作为信息提示或待确认项，不能用不可靠参考消费执行硬性过滤。
第一版使用周边搜索返回的直线距离；如后续需要通勤时间，只对排名靠前的少量酒店计算，不展示
完整导航路线。

## 9. 前后端职责

### 9.1 前端

- 展示快速入口、表单、地点联想和选择结果；
- 管理未提交的临时表单草稿；
- 不自行认定地点、字段冲突或 `planning_ready`；
- 提交人类可读消息和结构化 `trip_input`；
- 使用现有流式进度、补全卡和答案卡展示结果。

### 9.2 无状态地点服务

- 代理地图平台地点提示、POI 详情、地址解析和酒店周边搜索；
- 规范化第三方响应，隐藏供应商 Key；
- 实施超时、限流、缓存和错误映射；
- 不创建 Run、Goal 或 `active_trip`；
- 不接收与地点查询无关的公司政策、用户身份或出差目的。

### 9.3 编排层

- 将明确的快速差旅提交授权为现有 `itinerary_planning`；
- 把结构化字段交给 `event_collection`；
- 复用现有 DAG、暂停恢复、记忆 Hook、Composer 和合规检查；
- 决定可选能力是否执行并处理降级。

## 10. 安全、隐私与数据质量

1. 地图服务 Key 只保存在服务端环境变量中，不进入前端、日志和答案；
2. 发送给地图服务的内容只包含地点关键词、城市限制、POI ID 或坐标；
3. 不发送用户姓名、公司制度、出差目的或完整对话；
4. 对客户/会议地址的日志做截断或脱敏，并限制缓存保留时间；
5. 国内坐标统一使用高德坐标体系，禁止混用未经转换的 WGS84/BD-09；
6. 第三方结果缺字段时按“未知”处理，不由 LLM 补造评分、价格、电话或地址；
7. 上线前确认地图数据、图片、缓存和来源标识符合平台协议。

## 11. 实施拆分

### 阶段一：快速表单与 Workflow 复用

- 新增快速差旅入口与响应式表单；
- 复用 `FIELD_SPECS` 和现有行程校验定义；
- 扩展现有聊天请求以接收 `trip_input`；
- 完整字段直接进入 `plan-trip`；
- 缺失字段仍输出现有补全卡；
- 已有等待 Run 时验证恢复同一 Goal。

### 阶段二：结构化地点选择

- 接入城市/行政区候选；
- 接入会议地点 POI/地址候选；
- 增加服务端候选校验和规范化模型；
- 支持近期地点和已确认常驻地快捷选择；
- 覆盖无结果、服务不可用和地点编辑后失效场景。

### 阶段三：附近酒店推荐

- 在现有 `information_query` 中增加 `nearby_hotels` capability；
- 规范化酒店信息并实现可解释排序；
- 新增酒店卡片与高德打开链接；
- 明确参考消费、实时价格和合规状态的展示边界。

## 12. 验收标准

### 12.1 主流程

- 用户可以不经过逐轮问答，一次选择完整信息并启动标准 `plan-trip` Workflow；
- 请求只创建 `itinerary_planning` Goal，不出现 `quick_trip` intent/Goal/Workflow；
- 完整信息不进入无意义的 `WAITING_USER`；
- 不完整信息使用现有补全卡和同一 Run 续跑；
- 已有等待任务时，快速表单提交恢复原 Run 和原 Goal；
- 重复 `request_id` 不产生重复 Run、Goal、记忆写入或酒店查询副作用。

### 12.2 地点

- 目的地必须选择经过验证的城市/行政区候选；
- 开启酒店推荐时，会议地点必须选择经过验证的 POI/地址候选；
- 编辑已选文字会使旧地点选择失效；
- 私人会议室可通过“地理锚点 + 地点说明”表达；
- 地图服务不可用时可以关闭酒店推荐并继续基础差旅规划；
- 未确认地点不能生成具体附近酒店结果。

### 12.3 酒店

- 推荐结果围绕会议地点而不是城市中心；
- 展示来源、距离和推荐理由；
- 缺失字段不会被模型补造；
- 参考消费不显示为实时房价；
- 无可靠价格时不输出确定的住宿费用合规结论；
- 酒店服务失败不会导致整个 `plan-trip` Run 失败。

## 13. 测试范围

### 13.1 前端测试

- 快速入口在首页和聊天页可访问；
- 必填字段未完成时提交按钮禁用；
- 地点只输入未选择时不可提交；
- 选中地点后编辑文字会清除结构化选择；
- 日期自动计算时长；
- 移动端底部面板和桌面端抽屉可正常操作；
- 提交期间防重复点击，失败后可重试。

### 13.2 后端与编排测试

- `trip_input` 被映射到现有 `itinerary_planning`；
- 不产生新的 intent、Goal 类型或状态表记录；
- `event_collection` 仍是字段校验权威；
- 完整、缺失、冲突三类输入分别进入正确状态；
- 等待中 Run 使用快速表单补齐后恢复同一 Goal；
- Workflow 图定义变化仍受 `graph_hash` 保护；
- 地点服务超时、限流、空结果和畸形结果均安全降级；
- 酒店查询只在满足坐标与 capability 条件时执行；
- 酒店结果不可用时 `on_failure: continue` 生效。

### 13.3 数据安全测试

- 服务端 Key 不出现在 HTML、API 响应、日志或持久化消息中；
- 浏览器伪造 POI ID、坐标或 `verified=true` 会被后端拒绝；
- 地点查询不会携带公司政策、出差目的和对话历史；
- 第三方返回文本经过长度、类型和展示安全校验。

## 14. 最终边界

系统仍只有一条差旅规划主链路：

```text
自然语言聊天 ───────┐
行程补全卡 ─────────┼─→ itinerary_planning → plan-trip Workflow
快速差旅表单 ───────┘
```
