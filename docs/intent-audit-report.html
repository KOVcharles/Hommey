02

管线内部精确变换链

每个环节的职责与代码一一对应 —— 评估工作流时逐环节核过，以下顺序即真实执行顺序。

  1. 归一化 — _normalize_input 去空白，产出 agent_query（喂模型）/ display_message（展示）；附件 fail-closed。
  2. 恢复孤儿 Run — get_active 发现 ACTIVE 但 current_request_id ≠ 本次 request_id → recover_orphaned_active_run 标 INTERRUPTED 转可恢复（持 per-user 锁）。
  3. 回合分类 — TurnResolver.resolve：显式「继续」→ resume；WAITING_USER 下按 new-goal 标记 / 未激活意图 / 槽位更新三态分类；INTERRUPTED 下按同意图 / 任务修订 / 新目标分类。
  4. 意图识别 — 非 resume：guard →（无历史）快路由 → LLM 分类 → _apply_routing_guard 合并快路由候选 + _should_call_intent 重算授权 → 选 primary。
  5. 进入编排的闸门 — supports_task_pipeline：恰有一个可调用意图且全部可调用意图都是 skill-backed → 才进编排；否则走澄清 / chitchat 分支。
  6. 分解 — TaskDecomposer.decompose → LLM 语义任务字典；除 ExecutionLimitExceeded 外的失败 → 正则 fallback（每意图一任务）。
  7. 校验 — TaskValidator.validate → pydantic 强类型、按意图去重、越权 / scope / 自依赖 / 环 / 遗漏全拒；ValueError → pipeline 用 fallback 重试一次，二次失败才向上抛。
  8. 编译 — TaskGraphBuilder.compile → 每 IntentTask 展开为多步 ExecutionTask（{intent}-{agent_name}，goal_id = IntentTask.task_id），依赖边 + Kahn 拓扑分批。
  9. 持久化 — state_store.create_run / add_goals → 全量快照 + graph_hash；追加 goal 时 _namespace_new_goals 重命名保 Goal 身份。
  10. 执行 — TaskExecutor.execute → 每批并发 _run_one（含中断轮询 + result_rules + abort 传播 + pause 冻结）。
  11. 组合 — AnswerComposer.compose → LLM 组装 + AnswerDocumentValidator 接地 → 失败 FallbackComposer。
  12. 记忆回写 — MemoryHookExecutor.apply → 仅 status=success 触发的声明式 memory_hooks（per-hook try/except 吞错）。
  13. 终态 — lifecycle.mark_completed / mark_waiting / mark_interrupted → Run 终态 + 保留期。
  14. 恢复 — resume 路径：start_turn（focused WAITING goal 或全部 INTERRUPTED goal）→ 从快照重建任务 → 合并已提交节点结果回 entities → 重编译并要求 graph_hash 一致（否则 RuntimeError）→ 重执行。

03

关键设计点

以下设计决定都是刻意为之且经核实成立 —— 评估「bug 从哪来」必须先知道「本意是什么」。

DESIGN意图 ↔ Skill 1:1 单一目录

core/intent_catalog.py 从 .agents/skills/*/hommey.yaml 在 import 时构建 SKILL_INTENTS，15+ 个派生 helper（执行步骤、answer spec、置信度门、memory hooks、pause spec…）全部声明式派生，无 Python 侧硬编码。

DESIGN授权边界分层

guard（确定性）→ 快路由（廉价、仅授权不建计划）→ LLM（完整分类）→ _should_call_intent（可调用性授权）→ TaskValidator（意图级授权，LLM 永远不能命名可执行体）。

DESIGN确定性兜底

decomposer 失败 → 正则 fallback；validate 失败 → fallback 重试一次；compose 失败 → FallbackComposer。ExecutionLimitExceeded 一律向上抛（除 composer，见 P2-3）。

DESIGN状态机驱动恢复

Run / Turn / Goal / Node 四级；pause（WAITING_USER）+ interrupt + resume 均由 state_store 全量快照驱动；resume 只唤醒 focused goal + 跳过已提交节点。

BOUNDARY非用户入口的边

hommey_mcp/ 不是用户查询入口，是 skill agent 的工具提供方；CLI 已不存在（core/onboarding.py、scripts/benchmark.py 留有 vestigial 引用）。

05

共性根因

23 项缺陷可以收敛为 5 个模式 —— 修根因比逐条打补丁高效得多。

R1

快捷路径是主要风险源。 P1-1 / P1-3 / P2-2 全部来自「高置信度短路」—— 快路由 / 启发式为了省一次 LLM 调用，把判断权交给脆弱的子串 / 长度规则。设计文档说「只在高置信度、可证明无歧义时短路」，但 CHITCHAT_KEYWORDS 子串匹配和 len≤8 规则明显不满足「可证明无歧义」。

R2

校验器校验方向单一。 answer_validator 只查 result→section，不查反向；只查数字，不查非数字；数字又是全语料子串 —— 接地的名义比实际强。

R3

异常吞掉导致静默状态漂移。 composer 吞 ExecutionLimitExceeded、memory_hooks 吞写回失败、_file_get 吞损坏 —— 三处都是「宁可静默也不打扰用户」，但都留下不一致状态，且无任何指标 / 日志暴露。

R4

声明式配置与执行脱节。 mcp-tool 的 enabled_by_default / risk_level、event_collection 的 require_section 都是「对一种上下文正确、对另一种上下文危险」的配置，而代码没有区分调用上下文。

R5

多 goal 并发与持久化的交互没测到。 abort 传播 break、mark_waiting 覆盖、memory hooks 跳过，全部是「同批多 goal」场景 —— 现有测试大多是单 goal。

P0 是立刻该修、且改动量小、风险最低的项；P1 影响正确性；P2 建议与下一个功能迭代一起做。

07

测试覆盖缺口

基线 120 个测试全绿，但都命中「单 goal、构造正确、无对抗」的路径 —— 这就是问题能漏过去的原因。

✗带寒暄前缀的业务查询（P1-1）
✗多 goal 同批中两个 abort 失败（P1-4）
✗>12 天行程 / >12 goal 的组合（P1-2）
✗跨 turn 双 goal 暂停（P1-5）
✗数字跨 goal 伪造 / 精度改写的对抗用例（P2-1）
✗非数字编造事实（P2-6）
✗声明式安全标志的执行一致性（P2-4）
✓已覆盖：guard 精确匹配、快路由正确性、多意图路由不变量、DAG 编译 / 校验 / 执行、状态持久化、resume
方法学　3 个路由映射智能体 + 5 个 bug 猎手 + 24 项发现各配对抗性验证智能体 = 32 个智能体、≈200 万 subagent token、0 失败、17.9 分钟。 每项发现由独立验证智能体以「默认要推翻它」的立场复核代码 + 尝试复现，存活者才进入本报告； 本人另对全部核心文件逐行审读并独立复现了 P1 四项。
报告正文　工作流一节来自路由映射智能体产物并经逐行核对；缺陷列表每项均附 file:line 与验证来源，可直接定位修复。
